Trust, Recovery & Evidence

AI Risk Twin

Architecture-first, evidence-seeking AI risk pre-check: reconstruct the system from artifacts, then prove what's risky.

1The problem

AI risk assessment is a static questionnaire that asks developers to self-report risk. Developers assert 'the agent is read-only' while the architecture shows POST /holdTransaction — and nobody checks.

2The current gap

Answer-seeking tools trust assertions. Nothing reconstructs the system from architecture diagrams, IaC, and MCP manifests; nothing cross-checks documentation against the graph; nothing distinguishes a finding backed by runtime telemetry from one backed by a checkbox.

3How the solution addresses it

An evidence-seeking pipeline: ingest artifacts → build the AI use-case twin (components, flows, identities, trust boundaries) with three-level parsing that never trusts the diagram (edges resolve against IaC into real access paths) → 28-rule knowledge engine (OWASP Agentic/LLM, GDPR, EU AI Act, NIST AI RMF, internal policy) → dynamic funnel (125 questions → triggered → auto-answered → evidence-required → clarification) → evidence hierarchy L0–L5 → design vs information findings → readiness score → fix-and-rerun diff → drift detection.

6Insights

  • Artifact wins on disagreement. When docs say read-only and the graph shows a write edge, the graph is right.
  • Evidence has levels. L1 user assertion carries a 0.90 uncertainty penalty; L4 enterprise-system evidence 0.05. Confidence is computed, not claimed.
  • Readiness is separate from risk. 'Not ready for CISO submission' (3 blocking evidence items) is a different statement from 'risky' — and more actionable.
